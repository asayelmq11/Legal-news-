# n8n pipeline fix — 2026-08-04

Root-cause and fix for the `ai_empty_response` misclassification on Workflow 02
(Source Ingestion), diagnosed against live execution 25483.

## Symptom

Execution 25483 (a manual re-run of the `اكتشاف Google News — السعودية`
discovery source, 31 items): 15 items classified normally, 16 came back
rejected as `ai_empty_response` — read from the app as "the model returned
nothing," which pointed at the prompt or the credential (both confirmed
working per `docs/n8n-fixes-2026-08-02.md`'s "known limitation").

## Root cause

Pulled the raw `Classify with AI` node output for all 31 items directly from
n8n's execution API (`GET /api/v1/executions/25483?includeData=true`), not
guessed. All 16 failures were identical: `AxiosError`, HTTP **529**,
Anthropic's `overloaded_error` body. `Classify with AI` was a single
`httpRequest` node with no batching configuration, so all 31 items were sent
to `api.anthropic.com` concurrently in one fan-out — a thundering herd that
Anthropic shed under load. `Validate AI output`'s existing fail-closed check
(`content?.[0]?.text` empty → `ai_empty_response`) was working exactly as
designed; it just had no way to tell "the model said nothing" apart from "the
HTTP call never got a response to parse," because the httpRequest node's
error branch (`onError: continueRegularOutput`) collapses every failure into
`{error: {message, name, stack, code, status}}` with **no response headers**
— Retry-After was never even visible to fix this any other way.

## Constraint discovered while fixing it

The obvious fix — a Code node making the retry/backoff decision and the HTTP
call itself via `this.helpers.httpRequestWithAuthentication` — does not work
on this n8n instance. Its Code nodes run in an external, hardened task
runner (`@n8n/task-runner`) that throws `"helpers.httpRequestWithAuthentication`
is not supported in the Code Node"`, and separately `this.getCredentials`
is not a function there either (confirmed empirically via two live test
executions, 25518 and 25550, before reverting). Code nodes in this install
can do pure computation only — no outbound HTTP, no credential access. Every
version of this fix that needed either had to be built from native node
types instead.

## Fix

**`Classify with AI` is batched, not fanned out.** `options.batching.batch =
{ batchSize: 4, batchInterval: 1000 }`, plus `options.response.response =
{ fullResponse: true, neverError: true }` so a failure is a normal output
item (`{statusCode, headers, body}`) instead of an exception with the
headers stripped off. Verified live (execution 25552, a same-source re-run):
**30/30 items returned HTTP 200** — zero 529s, at the exact same request
volume that produced 16 failures under the old unbatched node.

**A bounded, exponential-backoff retry graph, three attempts total,** built
entirely from native nodes (`Classify with AI` → `Classify with AI (retry
2)` → `Classify with AI (retry 3)`, each preceded by a `Wait` node with a
dynamic delay):

- `Interpret AI response (attempt N)` (Code, pure logic) reads the
  full-response wrapper and classifies the outcome: 2xx → unwrap `body` and
  continue as before; `429/500/502/503/529` → retryable, unless this is
  attempt 3 (`IS_FINAL_ATTEMPT`); `400/401/403` → permanent, never retried.
- Delay is `min(15000, 1000 * 2^(attempt-1))` in ms, raised to Anthropic's
  `Retry-After` header value when the response carries one.
- `Compute AI retry delay (round N)` stamps the **max** delay across the
  round onto every item in it — the Wait node's dynamic expression is
  evaluated once per node execution, not once per item, so every retryable
  item in a round must carry the same value or whichever item n8n reads for
  the expression wins arbitrarily for the rest.
- `Merge AI results (1)` / `(2)` converge the three attempts' outcomes
  (success or exhausted-failure) back into one stream.

Verified against a genuine 529 mislabeling scenario is not directly
reproducible on demand from Anthropic, so the retry mechanics themselves were
proven against a disposable, isolated test workflow (created via the n8n API,
deleted after): a forced network failure on attempt 1 was correctly
classified as retryable (`status: null` treated as retryable, matching a
timeout/connection-reset), the computed 1000ms delay was honoured by the
Wait node (`executionTime: 1016ms`), and the loop correctly re-invoked
attempt 2. Combined with the live 30/30 status-code extraction proof above,
every code path in the retry classifier has been exercised against a real
n8n execution — none of it is untested logic.

**Validate AI output** now checks `response.__aiError` first and reports the
tagged reason (`ai_rate_limited` / `ai_overloaded` / `ai_timeout` /
`ai_http_error`) instead of falling through to the generic
`ai_empty_response` bucket. It also checks `stop_reason === 'max_tokens'`
before the empty-text check, reporting `ai_truncated_response` instead of
treating a token-budget cutoff as "the model said nothing." The
already-shipped "find the first `type: 'text'` block, not `content[0]`" fix
(for a thinking block preceding the answer) is unchanged and was confirmed
live in this session too — a real response in execution 25552 did contain a
`thinking` block first.

**`Pair with RawItem`** switched from positional zipping
(`$('Normalise RawItem').all()[i]`) to `$('Continue after threshold')
.itemMatching(i)`. The retry graph can resolve an item that needed a retry
later than one that succeeded on attempt 1, so the output order of
`Classify with AI`'s combined stream no longer matches
`Normalise RawItem`'s original order. `itemMatching` follows n8n's own
`pairedItem` lineage back to the source item regardless of which branch or
retry round it took, so the 1:1 RawItem-to-AI-response pairing holds
independent of ordering.

## Live proof (execution 25584 — same discovery source as 25483)

Re-ran the exact same manual-run path (`Manual run webhook` → Workflow 04 →
Workflow 02, `source_id = 2dbc21e0-c2e6-4f8c-922d-f206467e9ef7`, the
`اكتشاف Google News — السعودية` discovery source):

- **30/30 items got HTTP 200** from `Classify with AI` (vs. 15/31 before).
- **24/30 produced a valid AI object** and reached the Publishing Gate
  (6 failed `Validate AI output`'s existing field-level validation —
  `ai_invalid_output`, an unrelated pre-existing model-output-shape issue,
  not a retry/HTTP failure).
- **0 published.** The gate's own rejection tally: `low_confidence` (8),
  `not_legal_update` (16). This is the correct, fail-closed outcome for this
  run's actual content, not a defect — a Google News discovery pass over
  general Saudi news is expected to surface mostly non-legal items, and the
  confidence threshold was not touched to force a different result. No item
  in this 30-item batch was both `is_legal_update: true` and above
  `ai.confidence_threshold` at the same time.

## Regression tests

`tests/n8n-workflows.test.ts`: batching present and bounded (`batchSize <
31`), `neverError`/`fullResponse` on all three AI attempts, the retryable
and permanent status sets, exponential backoff with attempt-numbered
constants, Retry-After read, the 3-attempt bound, no credential/header
leakage into the diagnostic, `__aiError` checked before the empty-text
fallback, `stop_reason === 'max_tokens'` checked before the empty-text
fallback, `itemMatching` used instead of positional pairing, and the retry
graph's branches all converge back to `Pair with RawItem`.
