# n8n pipeline fixes — 2026-08-02

Incident log for the live-workflow repair covering Workflows 01–04
(Source Scheduler, Source Ingestion, Publishing Gate, Retry/Health/Manual Run).
Backups of the pre-fix live state are under `n8n/backups/20260802T064500Z/`.

## Root causes

1. **Supabase read nodes stuck on the default `Create` operation.** `Get
   settings`, `Get active sources` (01), `Get threshold` (02), `Re-read
   source`, `Look up hash` (03), `Settings`, `All sources` (04) all had no
   `operation` set, defaulting to Create with no field mapping — each
   attempted to insert an all-null row and hit a NOT NULL constraint instead
   of reading. Fixed to `getAll` (`Re-read source` / `Look up hash` also gained
   a `filters` condition scoping them to the current source/hash).

2. **`new URL()` is not available in this n8n Code node runtime.** Every use
   threw `URL is not defined`. Replaced with regex-based hostname/origin
   extraction in `HTML → RawItem` (02) and `Apply the five rules` (03).

3. **Workflow 04 contained a full, live duplicate of Workflow 01's hourly
   scheduler**, plus an orphaned duplicate of Workflows 02+03's ingestion and
   gate logic (42 nodes total). The duplicate scheduler fired every hour in
   parallel with 01, double-scheduling every due source and independently
   hitting the same NOT NULL bug. The ingestion/gate duplicate was unreachable
   (nothing referenced its `executeWorkflowTrigger`) but still audited as risk
   surface. Both were deleted; 04 now only calls 02 and 03 by `Execute
   Workflow`.

4. **Every `Execute Workflow` call defaulted to batching all input items into
   one sub-workflow invocation**, but every sub-workflow trigger reads
   `$('...').first()` — written for exactly one item. With 20 RSS items
   normalised in one run, only item 1 ever reached the Publishing Gate; items
   2–20 were silently dropped with no error. Set `mode: "each"` on every
   `Execute Workflow` node (`Run ingestion` in 01, `Publishing Gate` in 02,
   `Manual ingestion` / `Re-run ingestion` in 04).

5. **`Get threshold` was a dead-end node** (no outgoing connection),
   referenced only via `$('Get threshold')` from a much later node. n8n's
   execution planner can skip nodes that aren't on the path to a
   sub-workflow's own output, intermittently throwing `Node 'Get threshold'
   hasn't been executed'`. Rewired it into the real path: `Has items?` (new) →
   `Get threshold` → `Continue after threshold` (new, re-emits the normalised
   items) → `Classification prompt`.

6. **Items rejected during AI-response validation reached the Publishing Gate
   in a different shape** (`__item` instead of `item`, no `content_hash` at
   the expected path), so the gate's new source/hash lookups received
   `undefined` and Supabase rejected it as invalid UUID syntax instead of a
   clean rejection. `Prepare gate payload` (02) now normalises rejected
   entries into the same `item` shape as accepted ones; `Apply the five
   rules` (03) short-circuits on `__rejected` input and returns the original
   AI-validation reason instead of re-deriving (and misreporting as
   `missing_confidence_threshold`).

7. **A genuinely empty or failed run produced no `workflow_logs` row and no
   webhook response.** `Normalise RawItem` returning `[]` (nothing
   normalisable) or `Record fetch failure` running (fetch error) both
   dead-ended — every downstream node, including `Write workflow log`, is
   skipped by n8n when it receives zero input items. Added a `Has items?`
   branch with a `Build empty run summary` node, and wired `Record fetch
   failure` → `Build failed run summary`, both converging on `Write workflow
   log` with `status: 'empty'` / `'failed'`.

8. **The manual webhook had no deterministic response contract.** It relied
   on `responseMode: "lastNode"` (always HTTP 200, whatever the last node
   happened to output) plus `alwaysOutputData` on `Manual ingestion` as a
   patch. Switched to `responseMode: "responseNode"` with two explicit
   `Respond to Webhook` nodes returning `{ok, status, execution_id,
   correlation_id, processed, published, rejected, duplicates, failed}` and a
   status-appropriate HTTP code (200 completed/empty/skipped, 404
   source-not-found). `Resolve manual run` now also emits a marker item when a
   scope resolves to nothing, instead of returning `[]` and silently
   producing no response at all.

9. **`Manual run webhook` already had a native Header Auth credential bound**
   (`Header Auth account 2`) — this was correctly configured before this
   session; the removed piece was a redundant in-code secret check
   (`$env.N8N_TRIGGER_SECRET`, which this n8n install denies Code nodes
   access to). Verified live: no header → 403, wrong secret → 403, the real
   `N8N_TRIGGER_SECRET` from `.env.local` → accepted, confirming the header
   name n8n expects (`X-Trigger-Secret`) matches what `lib/ops/actions.ts`
   sends.

10. **`lib/ops/actions.ts` never read the n8n response body**, only
    `response.ok` — every 2xx response was reported to the admin as "Started"
    regardless of whether the run actually completed, published nothing, or
    was rejected. Updated to parse the JSON contract from fix #8 and show a
    status-appropriate Arabic message.

## Known limitation — not fixed in this session

The Claude API HTTP node (`Classify with AI`, Workflow 02) fails on every
call with `ERR_INVALID_HTTP_TOKEN` — a Node.js error meaning a request header
contains characters outside the HTTP token grammar. The request's own headers
(`anthropic-version`, `content-type`) are static ASCII, so the likely cause is
the stored `Header Auth account` credential's injected header (commonly a
pasted API key with a trailing newline or stray whitespace). Fixing this
requires opening that credential in the n8n UI, which is off-limits to this
session (credential contents may not be read or modified). Every item that
reaches classification is correctly and safely rejected as
`ai_empty_response` by the existing fail-closed validation in `Validate AI
output` — nothing malformed reaches `legal_updates` — but no item can be
published until the credential is fixed.

## PDF enrichment — not implemented

Umm Al-Qura's RSS feed (`https://www.uqn.gov.sa/rssFeed/pdf`) produces 20
items whose title/content is just the issue number (e.g. "العدد 5175"), not
the gazette's substance. Confirmed live: RSS fetch → XML parse → normalise →
all 20 items reach AI classification (blocked only by the credential issue
above). No enrichment step fetches the linked digital-issue page or the
underlying PDF; classification currently runs on the issue-number title alone,
which is unlikely to be sufficient for real legal classification. This is
scoped but not built.
